# Установка

Основной способ — Docker: три контейнера, веб-интерфейс (nginx), API и воркер
задач. API и воркер работают из одного образа, GPU получает только воркер.
Образы собираются на вашей машине. Установка без Docker — для разработки и
командной строки, см. [раздел в конце](#без-docker-разработка-и-командная-строка).

---

## 1. Что нужно на хосте

| Что | Зачем | Проверка |
|---|---|---|
| Docker 24+ с Compose v2 (2.20+) и **buildx** | сборка и запуск | `docker compose version`, `docker buildx version` |
| ~25 ГБ на диске | образ ~5 ГБ, модели ~11 ГБ, задачи | `df -h .` |
| ~16 ГБ оперативной памяти на время первой сборки | whisper.cpp и llama.cpp компилируются параллельно; при нехватке сборку убивает OOM (`BUILD_JOBS` в `.env` снижает число потоков) | `free -h` |
| **NVIDIA:** драйвер 525+ (CUDA 12) и NVIDIA Container Toolkit | GPU в контейнере | `nvidia-smi`, `docker info \| grep -i nvidia` |
| **Intel Arc:** драйвер Mesa с Vulkan | GPU в контейнере | `ls /dev/dri/renderD*` |

buildx в некоторых дистрибутивах — отдельный пакет: `docker-buildx` (Ubuntu
`docker.io`, Arch), `docker-buildx-plugin` (репозиторий Docker CE). Если
чего-то не хватает, `setup.sh` скажет, что поставить.

Без GPU всё работает на CPU, но медленно: выбор клипов локальной Qwen3-14B на
CPU идёт часами, поэтому `setup.sh` в таком случае предложит API-провайдера.

**NVIDIA.** CUDA toolkit нужен только для компиляции llama.cpp: сборка
скачивает образ `nvidia/cuda:*-devel` (~4 ГБ, на диске ~9 ГБ), а сам образ
приложения (~10 ГБ) его не содержит. Компиляция с CUDA долгая: под одну
видеокарту — до часа на 4-ядерном процессоре (в CI — 37 минут), поэтому
`setup.sh` собирает только под вашу карту (`CUDA_ARCHITECTURES`). Библиотеки CUDA 12 и cuDNN приходят вместе с torch,
драйвер — с хоста через NVIDIA Container Toolkit. После установки образ
toolkit можно удалить: `docker image rm nvidia/cuda:12.8.1-devel-ubuntu24.04`
(понадобится снова только при смене версии llama.cpp).

## 2. Установка

```bash
git clone https://github.com/ivbor-24/clips-pipeline.git && cd clips-pipeline
./setup.sh
```

Запускайте от своего пользователя, без `sudo`. Скрипт задаёт несколько
вопросов (у каждого есть ответ по умолчанию) и делает всё остальное сам:

| Шаг | Что происходит |
|---|---|
| 1. Docker | Проверяет Docker, Compose, buildx и доступ к Docker. Если чего-то нет, печатает команду для apt / pacman / dnf |
| 2. GPU | Находит NVIDIA или Intel и предлагает бэкенд `cuda` / `openvino` / `cpu`. Для NVIDIA проверяет драйвер и NVIDIA Container Toolkit и записывает compute capability карты (`CUDA_ARCHITECTURES`): llama.cpp компилируется только под неё. Для Intel берёт группу, которой принадлежит `/dev/dri/renderD*` (`RENDER_GID`) |
| 3. `.env` | Создаёт `.env` из `.env.example` или обновляет его. Вписывает `GPU_BACKEND` = `COMPOSE_PROFILES`, `HOST_UID` / `HOST_GID`, `RENDER_GID`, `MODELS_DIR` (предлагает каталог, где модели уже есть), доступ из локальной сети (только с паролем, `API_JWT_SECRET` генерирует сам) и свободный `WEB_PORT`. Остальные строки не трогает |
| 4. Каталоги и диск | Создаёт `data`, `jobs`, `uploads`, `cache/models` и `MODELS_DIR` от вашего пользователя, проверяет место под образ и модели |
| 5. Сборка | Проверяет, есть ли у контейнеров интернет, и собирает образы (`docker compose build`): 15–40 минут в первый раз, потому что llama.cpp (и whisper.cpp для Intel) компилируются под ваш процессор и GPU |
| 6. Модели и GPU | Скачивает модели распознавания речи, ключевых слов и лиц (~2 ГБ). Затем проверяет в контейнере воркера, что llama.cpp и whisper.cpp (Intel) или faster-whisper (NVIDIA) работают на GPU, что для Qwen3-14B хватает видеопамяти и каким кодировщиком будут кодироваться клипы (Quick Sync / NVENC или libx264 на CPU). После этого — LLM, без неё установка не завершается (см. ниже) |
| 7. Запуск | `just up` |

Уже скачанные модели проверяются по sha256 и заново не скачиваются. Задачи
работают без сети (`HF_HUB_OFFLINE=1`): модели скачивает только `setup.sh`.

Параметры: `--backend cpu|cuda|openvino`, `--models-dir DIR`, `--yes` (ответы
по умолчанию, без вопросов), `--no-models`, `--no-start`. Повторный запуск
безопасен: настройки сохраняются, готовые шаги сборки берутся из кэша.

**LLM обязательна**: клипы выбирает она. Если Qwen3-14B уже скачана или
API-провайдер уже настроен, `setup.sh` ничего не спрашивает. Иначе предлагает:

1. скачать Qwen3-14B (9 ГБ) и запускать её на этом компьютере — видео никуда
   не уходят;
2. подключить API-провайдера: OpenAI, Anthropic или сервис с OpenAI-совместимым
   API (DeepSeek, OpenRouter, свой сервер). Платно за запросы, и расшифровки
   видео отправляются провайдеру. Ключ записывается в `.env`
   (`OPENAI_API_KEY` / `ANTHROPIC_API_KEY`), провайдер и модель — в
   `data/settings.yaml` (их потом можно сменить на странице Settings). Сразу
   же воркер отправляет один короткий запрос: неверный ключ, модель или
   отсутствие связи видны при установке, а не в первой задаче;
3. остановиться и решить позже (`./setup.sh` ещё раз — образы уже собраны).

Если видеопамяти мало для Qwen3-14B, по умолчанию предлагается API. С `--yes`:
API-провайдер, если его ключ уже есть в `.env`, иначе скачивается Qwen3-14B.
Вернуться с API на локальную модель: на странице Settings выберите провайдера
`llama_cpp`, затем `./setup.sh` скачает её.

## 3. Запуск, остановка, состояние

```bash
just up        # веб-интерфейс: http://127.0.0.1:8080 (или ваш WEB_PORT)
just stop      # остановить; задача в работе вернётся в очередь
just status    # контейнеры, адрес, версия; что ещё запущено
```

Без `just` то же самое делает `scripts/stack.sh up|stop|status`.

`just up` проверяет, что запускать:

- уже запущено — печатает адрес и версию и ничего не трогает;
- запущена другая копия проекта (другой каталог) — предлагает её остановить:
  две копии делили бы один GPU;
- порт занят другой программой — говорит, какой, и предлагает сменить
  `WEB_PORT` в `.env`;
- воркер этой копии запущен вне Docker (`just dev`, `just worker`) —
  отказывается: два воркера брали бы задачи из одной базы.

**Выключение из веб-интерфейса.** Кнопка «Shut down» на главной странице
останавливает воркер, API и веб-интерфейс; память (в том числе видеопамять)
освобождается, клипы и настройки остаются. Если идёт задача, можно выбрать:
остановить её и продолжить с последнего этапа при следующем запуске,
дождаться её конца или отменить. Снова запустить: `just up`.

**Автовыключение.** Если 60 минут не открыта ни одна страница и нет задач в
работе и в очереди, система выключается сама (закрытая вкладка задачу не
прерывает). Срок — `API_IDLE_SHUTDOWN_MIN` в `.env`, `0` — не выключаться.

Контейнеры перезапускаются сами только после сбоя (`restart: on-failure`).
После перезагрузки компьютера система сама не стартует: выполните `just up`.
Незавершённые задачи продолжаются с последнего готового этапа.

Состояние воркера, проверка GPU, модели и место на диске — на странице
**Diagnostics** веб-интерфейса (кнопка на главной). «Copy report» копирует всё
это одним текстом: его удобно приложить к вопросу. Из консоли:

```bash
docker compose logs -f worker-openvino        # или worker-cuda, worker-cpu
docker compose run --rm worker-openvino python scripts/check_gpu.py --backend openvino
```

## Хранение, удаление и бэкап

**Автоочистка.** Через 30 дней после завершения задачи удаляется её исходное
видео: загруженный файл, его копия в задаче и аудио — около 2 ГБ на лекцию.
Клипы, субтитры, оценки и карточка задачи остаются, но продолжить или
перезапустить такую задачу уже нельзя, и её страница это показывает. Срок —
`cleanup.retention_days` на странице Settings, `0` — не удалять. Очистка идёт при
каждом запуске и раз в 6 часов, пока система работает. Загрузки, для которых
задача так и не была создана, удаляются через сутки.

**Удалить задачу целиком** — кнопка «Delete» на странице завершённой задачи
(клипы тоже удаляются).

**Бэкап.**

```bash
just backup                    # backups/backup-<дата>.tar: база задач, настройки, клипы
just backup --with-sources     # то же с исходными видео (~2 ГБ на лекцию)
just restore backups/backup-<дата>.tar
```

В бэкап входят база задач и оценок клипов, настройки веб-интерфейса
(`data/settings.yaml`), `.env` и каталоги задач (клипы, субтитры,
JSON-артефакты, логи). Исходные видео — только с `--with-sources`: без них
восстановленная задача сохраняет клипы, но продолжить её нельзя. Модели в бэкап
не входят никогда: `./setup.sh` скачает их заново. Архив доступен только вашему
пользователю: в `.env` и `data/settings.yaml` лежат пароль, секрет сессий и
(возможно) ключ API. Нужен `python3` на хосте (есть в Ubuntu и Debian).

`just restore` работает только при остановленной системе (`just stop`). Он
заменяет базу задач и настройки (`data/settings.yaml`) и записывает каталоги
задач (с теми же именами — поверх). Бэкапы, сделанные до появления страницы
Settings, несли `config/config.yaml` — при восстановлении он по-прежнему
применяется. `.env` не заменяется, потому что описывает эту машину (GPU,
пользователь, каталог моделей): копия из бэкапа ложится рядом как
`.env.from-backup`. Перед восстановлением текущие данные сохраняются в
`backups/before-restore-<дата>.tar`.

## Обновление

```bash
git pull
./setup.sh                                   # пересборка и новые модели; настройки не меняются
docker builder prune -f --filter until=24h   # кэш прошлых сборок, 5–10 ГБ за каждую
```

Схема базы задач обновляется сама при первом запуске новой версии; перед этим
рядом с базой остаётся её копия `data/api.db.before-<ревизия>`. Если база
создана более новой версией (например, после отката кода), сервисы не
запускаются и говорят, что делать: обновить код или восстановить бэкап этой
версии (`just restore`).

Данные лежат в каталогах проекта и переживают пересборку:

| Каталог | Что в нём |
|---|---|
| `data/` | база задач и оценок клипов, настройки веб-интерфейса (`settings.yaml`) |
| `jobs/` | рабочие каталоги задач: клипы, субтитры, артефакты |
| `uploads/` | загруженные видео |
| `cache/` | кэш транскрипций |
| `MODELS_DIR` | веса моделей |
| `backups/` | архивы `just backup` |
| `config/` | настройки пайплайна (bind-mount только для чтения; их страница Settings не трогает) |

## Если что-то не так

**`setup.sh` остановился с ошибкой** — в сообщении написано, что сделать;
после исправления запустите его снова.

**«Unknown host name …» (ошибка 403)** — без пароля API отвечает только на
`localhost`, IP-адреса и имена из `API_ALLOWED_HOSTS` в `.env`: так чужой сайт,
открытый в том же браузере, не может управлять системой через подмену DNS.
Открывайте интерфейс по `http://127.0.0.1:8080` или добавьте имя компьютера в
`API_ALLOWED_HOSTS` (через запятую) и выполните `just up`. Изменяющие запросы с
чужого сайта (заголовок `Origin`) отклоняются всегда.

**«Containers have no internet access on Docker's network»** — у хоста
интернет есть, у контейнеров нет. Чаще всего это файрвол (ufw, firewalld),
который не пропускает трафик из сетей Docker. `setup.sh` предлагает собирать
образы и качать модели через сеть хоста (`SETUP_NETWORK=host` в `.env`), и
этого достаточно для работы с загруженными видео. Задачи по ссылке (YouTube)
заработают, когда контейнеры получат доступ в интернет. С ufw частая причина —
`DEFAULT_FORWARD_POLICY="DROP"` в `/etc/default/ufw`: поставьте `"ACCEPT"` и
выполните `sudo ufw reload`.

**`check_gpu.py`: whisper.cpp или llama.cpp без GPU** — проверьте драйвер
(`vulkaninfo --summary` для Intel, `nvidia-smi` для NVIDIA) и запустите
`./setup.sh` снова: он пересоберёт образ под выбранный бэкенд.

**Сборка закончилась «exit code: 137» (out of memory)** — компилятору не
хватило оперативной памяти: whisper.cpp и llama.cpp собираются параллельно.
`setup.sh` сам снижает число параллельных задач сборки (`BUILD_JOBS=2` в
`.env`) и повторяет сборку один раз. Если не помогло — закройте другие
программы или поставьте `BUILD_JOBS=1` в `.env` и запустите `./setup.sh`
снова. Пустое `BUILD_JOBS` — автоматически: `min(nproc, RAM/4)`.

**Файлы в `jobs/` принадлежат root** — контейнеры запускались без `HOST_UID`.
`setup.sh` это замечает и печатает команду:
`sudo chown -R $(id -u):$(id -g) data jobs uploads cache`.

## Вручную, без `setup.sh`

Всё, что делает скрипт, можно сделать руками:

```bash
cp .env.example .env     # GPU_BACKEND = COMPOSE_PROFILES, HOST_UID/GID, RENDER_GID, MODELS_DIR, BUILD_JOBS
mkdir -p data jobs uploads cache/models models
docker compose build
docker compose run --rm prefetch-models
docker compose up -d
```

Каталоги нужно создать до первого запуска: иначе Docker создаст их от root.

## Образ для другой машины

Обычная `docker compose build` собирает под процессор этой машины.
`just image-build` собирает переносимый образ (`CPU_TARGET=portable`: только
AVX, без AVX2), который работает и на старых процессорах:

```bash
just image-build backend=openvino                 # образ pipeline:openvino-latest
just image-save image=pipeline:openvino-latest    # dist/<имя>.tar.gz и .sha256
# перенесите оба файла и клон проекта на другую машину, там:
just image-load dist/<имя>.tar.gz
docker tag pipeline:openvino-latest clips-pipeline:openvino   # имя, которое ждёт docker-compose.yml
```

Дальше — как в разделе [«Вручную, без `setup.sh`»](#вручную-без-setupsh), но без
`docker compose build`: `setup.sh` всегда собирает образ заново.

## Без Docker: разработка и командная строка

Для работы через веб-интерфейс рекомендуется Docker. Нативная установка нужна
для разработки и для обработки из командной строки.

```bash
./install.sh openvino    # или cpu, cuda: системные пакеты (на apt — сам, на других — печатает команду),
                         # зависимости из uv.lock, сборка llama.cpp (и whisper.cpp для Intel Arc), самопроверка GPU
just check-gpu           # ещё раз проверить, что llama.cpp и whisper.cpp работают на GPU
just prefetch-models     # скачать модели заранее, а не посреди первой задачи
just dev                 # API, воркер и веб-интерфейс разработки (http://127.0.0.1:5173); Ctrl+C останавливает всё
```

Режим GPU никогда не переходит на CPU молча: если GPU не используется,
`install.sh` объясняет причину и останавливается. Для Intel Arc задачи идут с
профилем `intel_arc` (whisper.cpp на Vulkan).

Обработка из командной строки, без веб-интерфейса:

```bash
just process видео.mp4                                         # все этапы
just process "https://www.youtube.com/watch?v=..."             # видео по ссылке
just process видео.mp4 config/config.yaml True                 # dry-run: только проверка конфигурации
just process видео.mp4 config/config.yaml False True           # resume: готовые этапы пропускаются
just process видео.mp4 config/config.yaml False False True     # force: всё заново
just process видео.mp4 config/config.yaml False False False intel_arc   # с профилем
```

Результаты — в `output/` (при `output.isolated: true` — в отдельном каталоге на
каждый запуск, см. [CONFIG.md](CONFIG.md)). Командная строка читает только
переданный ей файл конфигурации, без настроек со страницы Settings, — чтобы
запуск можно было повторить.
